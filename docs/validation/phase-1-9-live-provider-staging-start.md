## Objective

Validate at most one manually approved real AvalAI canary request through Simorgh's existing governed model path and reconcile its provider request ID against a bounded typed User API transaction lookup.

```text
manual protected staging run
  → provider/model/credit/policy preflight
  → fixed Core-authored canary
  → BudgetedModelGateway
  → durable InvocationStore reservation
  → one AvalAI provider request
  → durable terminal invocation and correlated Trace
  → bounded transaction lookup by provider request ID
  → sanitized typed validation artifact
```

The phase validates the existing runtime. It does not enable production or autonomous live model traffic.

## Current repository audit

At the Phase 1.8 merge base:

- `ModelProvider` is provider-neutral;
- `AvalAIProvider` uses the official OpenAI Python SDK with a configured custom base URL;
- `BudgetedModelGateway` performs policy-based model selection, worst-case reservation, durable invocation identity, exact replay and conservative unknown handling;
- `InvocationStore` and `TraceStore` preserve request, usage, replay and uncertainty authority;
- `AVALAI_API_KEY`, API base URL, User API base URL and default model are Core-only settings;
- ordinary CI contains no live-provider job;
- no narrowly scoped User API adapter, typed staging policy/result or manual live workflow exists yet.

AvalAI's current official documentation describes an OpenAI-compatible SDK boundary, model discovery, an `x-request-id` for API requests and a User API transaction lookup for exact cost. Transaction availability may be asynchronous; provider-call retry is not an acceptable response to delayed billing data.

## Approved implementation sequence

### 1. Strict staging contracts and policy

Introduce immutable versioned contracts for:

- disabled-by-default staging policy;
- provider/API/User-API base URL allowlists;
- reviewed model allowlist;
- one-call and bounded input/output-token limits;
- maximum estimated cost and minimum credit floor;
- bounded transaction polling;
- typed credit, model, provider request, exact transaction and reconciliation summaries;
- sanitized canonical staging result.

Unknown fields, non-finite numbers, negative values, ambiguous currency/unit fields and secret-like values fail closed.

### 2. Narrow AvalAI User API adapter

Allowed operations:

- read current credit summary;
- look up transaction IDs generated by the current staging run.

The adapter must have explicit timeouts, response-size/item limits, strict contracts, HTTPS base URL allowlist, typed 401/403/429/5xx failures and full secret/error redaction. It cannot accept arbitrary URLs, paths, methods or bodies from users/models.

### 3. Fake/local staging service

Build the complete live-run service against fake provider and User API adapters first.

It must prove:

- all preflight failures happen before provider entry;
- one fixed canary traverses BudgetedModelGateway and durable stores;
- provider transport uncertainty is durable and never retried automatically;
- exact completed replay causes zero provider/User API calls and zero new usage;
- transaction pending/available/unavailable and mismatch states remain distinct;
- exact cost above policy ceiling fails staging without rewriting invocation truth;
- prompt/output/credential/private transaction markers remain absent from stores, trace, logs and artifact.

### 4. Sanitized staging CLI and artifact

Provide a dedicated internal CLI/module that:

- receives only reviewed staging configuration;
- creates one staging run/request/invocation identity;
- uses the fixed canary;
- writes one schema-validated JSON artifact;
- verifies canonical hash and forbidden markers;
- never writes prompt/output text, headers, IP address, API-key suffix, cookie, raw provider response or environment dump.

### 5. Manual protected workflow

The live workflow must:

- use `workflow_dispatch` only;
- use a protected `live-provider-staging` environment;
- allow one concurrent live run;
- use minimal permissions;
- run local lint/type/fake tests before accessing the environment secret;
- expose `AVALAI_API_KEY` only to the live step;
- select a reviewed model and hard budget;
- make at most one provider request;
- upload only the sanitized artifact;
- exit nonzero on authority, budget, provider, reconciliation, privacy or artifact failure.

No pull request, push, schedule, API endpoint or model output can trigger the live run.

### 6. One explicitly approved live acceptance

The accepted live run must prove:

- at most one provider request;
- exact durable invocation and trace identities;
- bounded local estimated/committed usage;
- captured provider request ID;
- exact User API transaction lookup or explicit bounded pending/unavailable state;
- exact cost under the reviewed ceiling;
- no secret/private marker in logs or artifact;
- exact replay with the same invocation identity creates no second request or charge.

## Failure semantics

### Before provider entry

Credential, URL/model allowlist, model availability, credit-floor, budget or durable-store failure prevents the provider call and records zero provider usage.

### After durable reservation

If provider entry/completion is uncertain:

- preserve conservative durable usage;
- mark invocation `unknown` through existing authority;
- do not retry automatically;
- fail the staging run honestly.

### After provider completion

- validate provider/model/request identity and canary contract;
- durably terminalize before reporting success;
- User API failure cannot erase completion;
- unavailable transaction data remains explicit and never becomes zero cost;
- usage/cost/model/status mismatch fails staging without modifying the completed invocation.

### Trace/report failure

- never reissue the provider request;
- preserve InvocationStore truth;
- exact retry reads/reconciles the same identity;
- secrets/raw bodies remain absent from errors.

- no public model endpoint;
- no automatic or scheduled live test;
- no provider/model/domain failover;
- no streaming, multimodal, tools or batch provider validation;
- no live GitHub connector or complete GitHub report workflow;
- no mutation or Android action;
- no storage of prompt/output/raw provider/User API bodies;
