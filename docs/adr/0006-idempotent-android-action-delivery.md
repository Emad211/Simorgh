# ADR 0006: Idempotent Android action delivery with an encrypted write-ahead ledger

- Status: Accepted
- Date: 2026-07-24

## Context

Simorgh will eventually launch applications, click controls, enter text, scroll interfaces, and invoke Android global actions. These are external side effects. A WebSocket can disconnect after Android receives a command but before Core sees an acknowledgement or result. Android can also terminate the application process while an operation is active.

Traditional at-least-once message delivery would resend the command after reconnect. That is unacceptable for device operations because the repeated action may send a message twice, submit a form twice, toggle a setting back, or select a different element after the screen changes.

At-most-once delivery alone is also insufficient: dropping a command or result without durable evidence makes the system impossible to audit and prevents controlled recovery.

The design therefore needs separate identities, a durable device-side execution boundary, replay-safe results, and an explicit representation of uncertainty.

## Decision

Simorgh will use:

- one non-terminal action per device;
- a stable Core command envelope with distinct `message_id`, `command_id`, and `action_id`;
- exact command-envelope redelivery after reconnect;
- an encrypted Android write-ahead ledger persisted before executor submission;
- no automatic replay of an active ledger entry after process restart;
- a terminal blocked result when prior execution state is uncertain;
- one stable persisted result `message_id` until Core acknowledgement;
- typed command, result, cancellation, and acknowledgement messages;
- strict correlation checks at both ends;
- separate device and operator credentials;
- serialized Core WebSocket writes;
- dedicated result retry rather than the generic outbound queue.

### Identity roles

- Protocol `message_id` identifies one immutable wire message.
- `command_id` identifies one command instance generated by Core.
- `action_id` identifies the logical operation and status resource.
- `correlation_id` links an acknowledgement or result to the precise preceding message required by the protocol.

Identifier reuse with different content is a conflict, not an update.

### Crash rule

When Android reloads an `active` ledger entry and receives the same command again, it must not call the executor. It records and emits:

```text
outcome = blocked
failure_code = internal_error
attempts = 0
```

The detail explicitly says that execution state was unknown and the command was not re-executed.

This rule favors avoiding duplicate external side effects over pretending that an uncertain operation succeeded or failed.

### Result rule

After executor completion, Android persists the typed result and a generated result message ID before transport. Every retry and reconnect uses the same envelope identity and command correlation. A matching `accepted` or `duplicate` acknowledgement is persisted before the publisher clears its in-memory delivery.

## Consequences

### Positive

- A reconnect cannot create a second command identity.
- Process restart cannot silently repeat an uncertain side effect.
- Lost result acknowledgements are recoverable without rerunning the action.
- Core and Android can detect identifier/content conflicts.
- Every failure has a typed observable state.
- The future live executor can remain focused on one bounded operation and postcondition verification.

### Negative

- Some operations will end as `blocked` even when they may actually have succeeded before a crash.
- Recovery requires a fresh observation and possibly a newly planned command.
- The current Core broker is process-local and must later be backed by durable workflow state.
- Android retains a completed ledger entry until Core acknowledgement, blocking subsequent actions.
- The design is more complex than a fire-and-forget WebSocket message.

## Rejected alternatives

### At-least-once command execution

Rejected because retransmission can duplicate irreversible or user-visible side effects.

### Reuse the generic outbound queue

Rejected because queue eviction, regeneration of envelopes, or unrelated message ordering would violate stable result identity and action single-flight semantics.

### Store only an in-memory active action

Rejected because Android process death would erase the only evidence needed to prevent re-execution.

### Assume a successful Android API return proves success

Rejected because API acceptance does not prove the intended visible postcondition, and it provides no crash recovery evidence.

### Automatically inspect UI after restart and declare the old action complete

Rejected at the transport layer. UI interpretation belongs to a new, explicit recovery plan using fresh observation evidence; transport must not infer a side effect outcome.

### Put the AvalAI key on Android

Rejected because model credentials are unrelated to device transport and would expand the device compromise boundary.

## Follow-up

- Add a durable Core workflow store while preserving wire identities.
- Replace the shared development device token with per-device revocable pairing credentials.
- Implement the first real handler for `open_app` only.
- Require a fresh precondition observation and a newer post-action observation.
- Validate crash/reconnect scenarios on the Samsung Galaxy A53 before closing the action-executor epic.
